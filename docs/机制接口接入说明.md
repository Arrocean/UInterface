# 机制接口接入说明

## 选择接入方式

- 复用原版设备时，先通过 `ComponentApi.GetShipComponents(componentType, includeInactive)` 枚举艇体、舱内和当前艇已加载的依赖场景，或通过 `TryGetMountedComponent(mountId, componentType, out component)` 精确定位挂点上的组件。获得组件后使用它的原版公共方法。挂点定义由艇体内容包提供。
- 舱内需要船员执行的操作走 `StationApi`。它查询角色及工位的原版条件，然后提交原版动作。设备包可复用这条路径处理维护、装填、搬运、阀门和开关。
- 设备包提供新的数字控制台、动力设备或其他行为时，可在当前艇注册自己的子系统和控制件。内容包拥有模拟、输入界面、动画、状态与存档规则，通过稳定的 ID 让其他模块发现能力。

接口方法可通过游戏已加载的 `UInterface` 公共类型绑定为委托，参见 [中文 README 的 C# 接口说明](../README-zh_CN.md#c-接口)。API 在游戏主线程使用。船只、设备和动作对象属于当前游戏场景，每次换艇或读档后应重新获取。

## 由游戏模组管理器加载的内容包

依赖方在自己的 Mod 中引用 UBOAT 公共 API。通过游戏注入的 `UBOAT.Game.Core.Mods.IModManager` 查找 UInterface，在该程序集上查找方法。下面的 `mods` 为已注入的实例。

```csharp
var api = mods.GetMod("UInterface")?.Assembly?.GetType("UInterface.SubmarineApi");
var method = api?.GetMethod("GetFeatureVersion");
var featureVersion = method == null ? null :
    (Func<string, int>)Delegate.CreateDelegate(typeof(Func<string, int>), method);
bool operationsSupported = featureVersion != null &&
    featureVersion("uinterface.subsystem-operations") >= 1;
```

框架安装能力的版本在各加载步骤完成后可查询。现有能力 ID 包括 `uinterface.lifecycle`、`uinterface.dependency-scenes`、`uinterface.campaign`、`uinterface.port`、`uinterface.subsystem-operations` 和 `uinterface.submarine-actions`。`uinterface.propulsion-binding` 在首次成功注册推进组件绑定后可查询。依赖方在 `OnLoaded` 期间可以找到已编译的框架类型，能力尚未就绪时可在游戏进入下一阶段后重新查询。

0.10.0 增加 `uinterface.mounted-subsystems`、`uinterface.first-person-buttons` 和 `uinterface.native-sensor-observations`。

0.11.0 增加 `uinterface.propulsion-output`，在首次成功注册推进提供方后可查询。首次注册前可通过 `PropulsionApi.ApiVersion` 检查接口签名。

0.12.0 增加 `uinterface.power-supply`，在首次成功注册供电源或用电负载后可查询。首次注册前可通过 `PowerApi.ApiVersion` 检查接口签名。

0.13.0 增加 `uinterface.device-state`、`uinterface.first-person-axes`、`uinterface.first-person-hold`、`uinterface.sensor-contacts` 和 `uinterface.tube-requests`。`uinterface.station-templates` 在首次成功注册工位动作模板后可查询。

0.13.1 在首次成功加载对应补丁后提供 `uinterface.ammo-compatibility` 和 `uinterface.launch-spread`。

0.14.0 增加 `uinterface.sensor-contact-map`。`uinterface.power-interlocks` 可在首次安装舱室供电监听后查询。

独立设备包用 `SubsystemApi.RegisterOperations(id, version, operations)` 发布版本化操作。消费方通过 `TryGetOperation(id, minimumVersion, operationId, delegateType, out operation)` 获取签名约定的委托。双方可使用同一个标准类型，例如 `Func<string>`，无需各自定义同一个自制接口。通过 `GetOperationsVersion(id)` 和 `OnOperationsAvailabilityChanged` 可处理晚注册与卸载。艇上下文切换或收到下线通知时应释放缓存委托。已发布版本的操作签名兼容旧消费方，签名需要破坏性调整时使用新的子系统 ID。

## 玩家艇就绪与读档

订阅 `SubmarineApi.OnPlayerSubmarineReady`，并调用一次 `TryGetReadySubmarine` 接管已就绪的玩家艇。这个时点是在原版初始化和场景组件启动之后。读档时，这两个入口会等待原版加载协程结束，包括原版读档回调队列。内容包需要区分读档与正常装载时，可订阅同一轮就绪通知之后的 `OnPlayerSubmarineRestored`。

`OnPlayerSubmarineChanged` 仍在原版玩家艇引用切换时发出。换艇、卸载或开始读档时，框架先释放旧上下文的控件、收放设备、传感器、子系统和工位订阅，再发布下线通知。读档期间暂停艇型和挂点查询，结束后从已恢复的玩家艇刷新艇型 ID，再发送就绪通知。异步依赖场景中的挂点在各自场景加载后可查询，`TryGetMount` 会在艇体和舱内找不到路径时检查当前艇的依赖场景。

在 `OnPlayerSubmarineReady` 中先绑定已可用的设备，再用 `OnPlayerSubmarineDependencyReady(PlayerShip, Transform)` 补绑之后加载或重载的依赖场景。依赖场景卸载时，其控件、收放设备、传感器和工位订阅会释放。原有注册句柄可以安全地释放，重新注册的实例会保留。

## 设备状态随档保存

`DeviceStateApi.TryWrite(deviceId, version, data)` 为当前玩家艇保存一个设备的运行时状态。`version` 是大于零的内容格式版本，`data` 是字符串，可以包含 JSON。`TryRead(deviceId, out version, out data)` 读取状态。`TryRemove(deviceId)` 删除本次艇上下文中的记录。请给设备 ID 加内容包前缀。

状态随下一次游戏保存写入同一个存档文件。读档时，数据在 `OnPlayerSubmarineReady` 之前可读。旧存档和首次装载时，`TryRead` 返回 `false`，由内容包填写默认值。内容包可在状态变化时写入，自己负责升级数据格式及应用状态。换艇时重新建立当前设备的状态。每份存档最多 256 个条目，ID 最多 256 字节，每条数据最多 8192 个 UTF-8 字节。

## 工位与原版动作

`GetStations(stationId)` 枚举匹配的舱内工位。同一类可以有多个实例。稳定工位 ID 与挂点一一绑定时，可以使用 `TryGetStation` 精确取单项。

自制艇可用 `RegisterStationGroup(submarineId, stationId, mountIds)` 将多个挂点归到一个工位 ID，或在原数据行的 `Mounts` 列用逗号分隔填写挂点 ID。`Mounts` 有值时优先于单个 `Mount`。组内晚加载的成员可在依赖场景就绪后重新枚举。

`QueryNativeActions(station, actor)` 返回该工位对指定角色可见的原版动作及其可用状态。`RequestNativeAction(station, template, actor)` 使用查询返回的模板提交请求，提交前重新检查工位归属和原版可用状态。成功表示原版已接收任务，或已完成框架适配的即时操作，例如切换舱室电源或操舵模式。持续任务的完成状态由原版系统持有。已有的命名动作注册、查询和请求接口继续可用。

- `TryGetStationState(station, out hasAssignedCrew, out switchedOn, out operating)` 适用于关联原版 `Device` 的工位。`TryGetStationUsers(station, out users)` 和 `SubscribeStationStateChanged(station, callback)` 也适用于无设备关联的工位。有效且空闲的工位返回空船员数组。
- `RequestTrackedAction(stationId, actionId, actor)` 和 `RequestTrackedNativeAction(station, template, actor)` 返回可跟踪的原版 `CharacterAction` 实例。可先读 `Progress`、`Stage`，再订阅 `Changed`、`StageChanged`。对在预启动阶段完成的已适配原版操作，请用返回 `bool` 的请求入口判断是否执行。`null` 仅表示没有可跟踪实例。
- `TryCancelTrackedAction(actor, action)` 只接受此上下文中为该角色返回的实例，检查原版 `CanBeStopped`，然后从该角色队列移除指定动作，或者停止该角色正在执行的同一实例。
- `QueryNativeUtilityActions(station, actor)` 和 `RequestNativeUtilityAction(station, template, actor)` 使用原版辅助动作状态。查询与发起时可传 `null` 表示未选船员。原版用此模式直接打开部分储物界面。提交返回 `true` 表示调用了原版动作入口，包括打开界面即完成的交互。
- `QueryQueuedNativeActions(station, actor)` 查询队列模式下的工位任务。`RequestQueuedNativeAction(station, template, actor)` 有船员时追加到其个人队列，`actor` 为 `null` 时提交全艇队列，由原版分工。返回的动作实例可以用 `TryCancelQueuedNativeAction(action)` 取消。原版队列仍处理容量、任务替换及开始时机。打开储物界面及已适配的即时操作使用直接请求入口。
- 玩家艇就绪后，`GetActiveQueuedNativeActions(actor)` 返回指定原版队列中仍有效的玩家指派任务，包含从存档恢复的任务。`TryTrackQueuedNativeAction(actor, action)` 可接管其中一个实例，再用既有接口取消。`actor` 为 `null` 时查询或接管全艇队列。内容包可按工位和动作筛选需要接管的实例。
- `RegisterActionSelector(stationId, actionId, actionType, selector)` 用提供方的筛选器从同类型模板中确定唯一动作。`QueryStationActions`、`TryGetStationActionState`、`RequestStationAction`、`RequestTrackedStationAction` 都接收从工位组枚举出来的具体工位，按命名动作调用。
- `RegisterSubmarineAction(submarineId, stationId, actionId, actionType, selector)` 可为指定艇型选择具体原版动作。查询时优先采用当前艇型的同名绑定，其余动作沿用全局默认绑定。
- `RegisterActionTemplate(actionId, station, template)` 把新的原版 `CharacterAction` 模板添加到当前艇的指定工位。内容包负责实现资格判断、动作执行和完成条件。模板应支持 `Duplicate(station)`，例如提供接收源模板和工位的公共复制构造函数。查询可通过原版工位入口或 `StationApi`，直接提交或入队沿用上面的原版方法。释放注册会移除可选模板，已开始的任务可通过跟踪接口取消。若任务实例随档保存，读档时需要提供该类型的内容包。

原版艇提供以下工位 ID，由 `VanillaStations.cs` 映射到已查到的原版标签。新艇可在 `UInterfaceStations` 中将相应 ID 指向自己的挂点。

## 自定义控件、桅杆与子系统

以下注册返回 `IDisposable`。释放可撤销本次注册。换艇或读档会释放旧上下文的绑定，内容包可在就绪通知中重新注册。重复 ID 或资源尚不可用时返回 `null`。

- `ControlApi.RegisterButton(controlId, mountId, press)` 配对物理按钮与逻辑请求，`TryPress` 调用设备包提供的回调。
- `ControlApi.RegisterFirstPersonButton(controlId, mountId, press)` 在挂点上配置原版点击处理，并把当前第一人称船员传给 `Func<PlayableCharacter, bool>`。挂点需要布置可被原版第一人称交互命中的点击区域，已有原版点击组件的对象应使用其自身操作。内容包可通过 `CrewServicesApi.TryGetFirstPersonCrew` 查询当前第一人称船员，供旋钮或其他原版输入组件使用。
- `ControlApi.RegisterAxis(controlId, mountId, read, set)` 配对连续控件与设备状态，提供 `TryReadAxis`、`TrySetAxis` 和 `TryGetControlMount`。模型包的第一人称输入或数字界面调用这些方法，设备包负责其规则和反馈。
- `ControlApi.RegisterFirstPersonAxis(controlId, mountId, read, set, unitsPerPixel, vertical = false)` 把左键拖动交给原版第一人称的指针事件。默认按水平位移改值，可选垂直。灵敏度可取负值来反转方向。`set` 是 `Func<PlayableCharacter, float, bool>`，可检查船员资格并限制数值。挂点需要模型包配置原版射线可命中的区域，轨迹、动画和反馈由设备包实现。
- `ControlApi.RegisterFirstPersonHold(controlId, mountId, changed)` 通过 `Action<PlayableCharacter, bool>` 传递按下和松开。离开第一人称、失去窗口焦点、控件停用或释放注册时，正在按住的控件也会发送松开事件。
- `DeploymentApi.RegisterDeployable(equipmentId, request, readState)` 绑定设备已有的收放请求与状态。其他模块通过 `RequestDeployment` 和 `TryGetEquipmentState` 调用，实际动画、联锁与状态由设备包控制。
- `SubsystemApi.RegisterProvider(subsystemId, provider)` 注册艇内可选的子系统。`TryGetProvider(subsystemId, contract, out provider)` 用双方约定的类型查询。消费方和内容包决定契约，例如数字火控或供能系统。
- 子系统随局部场景加载时，用 `RegisterMountedProvider(subsystemId, mountId, provider)` 或 `RegisterMountedOperations(subsystemId, mountId, version, operations)`。挂点所属场景卸载时释放注册，并发出操作下线通知。整艇服务可以沿用原来的注册方法。
- `SensorsApi.RegisterSensor(equipmentId, provider, readState)` 将传感器绑定到已注册的设备挂点。通过 `TryGetSensor(equipmentId, contract, out provider)` 获取双方约定的接口，通过 `TryGetSensorState(equipmentId, out state)` 读取状态。提供方可在状态变化后调用 `NotifySensorStateChanged(equipmentId, provider)`，消费方按设备 ID 监听 `OnSensorStateChanged`，并在不再使用时解除事件订阅。传感器计算及观测发布由设备包接入其使用的系统。
- 独立显示模块可以先订阅 `OnSensorAvailabilityChanged(equipmentId, available)`，再用 `GetRegisteredSensorIds()` 获取当前清单。注册、释放、依赖场景卸载和艇上下文失效都会更新可用性。框架也会检测仍有注册项的传感器提供方是否已销毁，即使消费方没有发起查询。
- 已注册的传感器可调用 `SensorsApi.TryReportNativeObservation(equipmentId, provider, target, type, out observation)`，向原版观测系统报告雷达、雷达告警、听音或声纳接触。需要传入所属设备的当前提供方，以及原版已生成的游戏实体。这个方法使用原版的接触新增和刷新路径。传感器失去接触或卸载后停止报告，由原版按其规则让接触过期，共用同一接触的其他探测来源也由原版维护。

## 共享传感器接触

`SensorContactsApi.TryReportContact(sensorId, provider, contactId, bearing, sandboxPosition)` 由已注册的传感器创建或更新自己的接触。方位使用 0 至 360 度的游戏海图方位。坐标是可选的 `Vector2?` 沙盘坐标。只有方位时传 `null`。接触以传感器 ID 和接触 ID 联合标识，各传感器可分别报告同一目标。

显示台可用 `GetContactSources`、`GetContactIds(sensorId)` 和 `TryGetContact(sensorId, contactId, out bearing, out sandboxPosition)` 获取快照。`OnContactChanged(sensorId, contactId, present)` 通知创建、更新和移除。提供方用 `TryRemoveContact` 撤销失去的接触，设备释放时清理剩余接触。显示台负责融合、筛选和呈现。需要进入原版观测系统的已生成实体可同时走 `TryReportNativeObservation`。

共享接触会出现在原版普通海图和战术海图。有坐标的接触显示为琥珀色空心菱形。只有方位的接触从最近报告时的本艇位置画出虚线方向，随海图平移和缩放。撤销接触或释放传感器后，标记一起消失。标记仅展示传感器报告的数据，不参与地图的点击和目标选择。

## 配平泵与排水

`EngineeringApi.GetTrimPumps(includeInactive)` 支持多泵。`TryGetTrimPumpTanks(pump, out tanks)` 返回指定原版泵所连接的舱柜引用快照，可以读取舱柜水量。该接口读取游戏原有管路配置。开关和排水继续由原版泵与工位动作执行。

## 自制艇推进

原版 `PlayerShip` 在启动、进出港和档位切换中需要水面与水下两路 `PlayerShipEngine`。艇体包可以在 Unity Inspector 里填入这两个引用。需要在运行时按路径赋值的艇体可在装载前调用 `EngineeringApi.RegisterNativePropulsionBinding(submarineId, surfaceEnginePath, submergedEnginePath)`。先注册自制艇定义，再注册推进绑定。路径相对于艇体或舱内根对象。两个路径各需一个独立的 `PlayerShipEngine`，并在同一对象配置 `Interactable`。推进组件应位于初始艇场景。原版读档先按场景名启动艇体，所以使用这项运行时绑定的自制艇需要唯一的初始场景名。

两路组件可以使用自制模型和数据，供原版玩家艇调用。其中的原版发动机引用继续承载启动、车钟、进出港、燃油与电力消耗、充电、噪声和船员任务。动力包可单独实现推进模型，从下面的接口向原版螺旋桨提供功率，并可提供玩家艇的目标航速 `Ship.TargetVelocity`。动力包可通过 `SubsystemApi` 对外公开自己的设备状态与控制操作。

### 推进输出

`PropulsionApi.RegisterProvider(ship, resolvePower, resolveTargetSpeed)` 在玩家艇就绪后调用，每艘当前玩家艇可登记一个提供方。两个回调签名均为 `Func<PlayerShipEngine, float, float>`。回调接收当前原版发动机和原版输出，返回同单位的替换值。可传 `null` 让该项沿用原版，两项至少提供一项。

| 参数 | 返回值 |
| --- | --- |
| `resolvePower` | 螺旋桨有符号的归一化功率，倒车取负值。框架按当前发动机的 `MaxPower` 限幅，原版随后应用航线距离减速。 |
| `resolveTargetSpeed` | 米每秒，取非负速度。原版在处理目标深度和水听器检查时决定何时更新此值。 |

框架在当前艇的原版更新流程中按需读取回调。内容包应提前计算状态，让回调只读取结果。停档、锁档、设备停用、原地充电、停泊或原版工位性能不足时，框架将已注册的对应输出设为零。回调返回非有限数值或抛出异常时，该项使用原版值。负目标航速同样回退。未注册提供方的艇使用原版推进。

内容包在 `OnPlayerSubmarineReady` 接到自身支持的艇时注册，也可用 `TryGetReadySubmarine` 接管已就绪的艇。注册失败会返回 `null`。释放返回的 `IDisposable` 后，下次原版更新使用原版输出。换艇、读档及卸载会自动释放旧注册，内容包在下一次就绪时重新注册。

通过游戏模组管理器绑定的签名如下。`ship` 是本次就绪的玩家艇，`resolvePower` 和 `resolveTargetSpeed` 由内容包定义。

```csharp
var api = mods.GetMod("UInterface")?.Assembly?.GetType("UInterface.PropulsionApi");
var method = api?.GetMethod("RegisterProvider");
var signature = typeof(Func<PlayerShip, Func<PlayerShipEngine, float, float>,
    Func<PlayerShipEngine, float, float>, IDisposable>);
var register = method == null ? null :
    (Func<PlayerShip, Func<PlayerShipEngine, float, float>,
        Func<PlayerShipEngine, float, float>, IDisposable>)Delegate.CreateDelegate(signature, method);
var registration = register?.Invoke(ship, resolvePower, resolveTargetSpeed);
```

## 电力接入

原版柴油机可以直接推进，也能给电池充电。原版电机通过 `PlayerShip.Energy` 计入电池耗电。独立动力包可以接入同一个电池，让发电设备向电池供电，由原版电机负责推进。采用持续电推的内容包可用原版 `PlayerShip.PreferredEngineOnSurface` 选择 `PlayerShipEngineType.Electric`。原版启动、进出港和档位仍需要两路发动机组件。

| 接口 | 职责 |
| --- | --- |
| `RegisterSource(ship, id, initialRate, out setRate, mountId = null)` | 注册一个发电源，向电池结算增加供电速率。 |
| `RegisterLoad(ship, id, initialRate, out setRate, mountId = null)` | 注册一个用电负载，向电池结算增加耗电速率。 |
| `RegisterInterlockedLoad(ship, id, initialRate, compartment, powerChanged, out setRate, mountId = null)` | 注册受指定原版舱室供电控制的负载，并接收通电或断电通知。 |
| `TryGetLoadPower(id, out powered)` | 即时读取联锁负载是否通电。 |
| `TryGetBattery(out charge, out capacity)` | 读取原版电池的当前电量与容量。 |
| `TryGetCustomPowerRates(out generation, out consumption)` | 读取所有自定义供电和当前生效的用电速率，两项均为非负数。 |

速率使用原版电池单位每个沙盘模拟秒。电池容量为 `1` 时，`0.001f` 等于每模拟秒增加或扣除电池容量的千分之一，再由原版结算应用充电倍率、容量上下限和耗尽通知。自定义供电和用电先取差额，再和原版发电、耗电一起结算。原版电池条反映结算后的电量，自定义供电和用电的合计速率由内容模块通过 `TryGetCustomPowerRates` 读取。动力包自行处理发电设备启停与状态保存。

在 `OnPlayerSubmarineReady` 中为当前艇注册。供电源与用电负载共用 ID，建议使用内容包自己的前缀。`setRate` 为 `Func<float, bool>`，传入有限的非负数，返回是否已更新。用 `0` 暂停供能或用电，释放 `IDisposable` 结束本次注册。换艇和读档自动结束旧注册。指定 `mountId` 时，挂点场景卸载也会结束注册。旧的更新委托不能修改重新注册的设备。

联锁负载在电池有电且指定舱室通电时参与结算。原版配电板断电、舱室手动关电或电池耗尽都会停扣该负载。断电时仍可更新请求速率，恢复通电后采用最新值。`powerChanged` 为可选的 `Action<bool>`，初始状态和变化会在原版状态更新后通知。设备包在回调中停启自己的设备，也可通过 `TryGetLoadPower` 处理即时操作。释放已收到通电通知的负载时，会收到最后一次断电通知。

通过游戏模组管理器取得 `RegisterSource` 委托。`RegisterLoad` 使用同样的签名。`ship` 是当前就绪的玩家艇。

```csharp
// Declare this delegate in the content mod.
delegate IDisposable RegisterPower(PlayerShip ship, string id, float initialRate,
    out Func<float, bool> setRate, string mountId);
```

```csharp
var api = mods.GetMod("UInterface")?.Assembly?.GetType("UInterface.PowerApi");
var method = api?.GetMethod("RegisterSource");
var register = method == null ? null :
    (RegisterPower)Delegate.CreateDelegate(typeof(RegisterPower), method);
if (register != null)
{
    registration = register(ship, "example.generator", 0f, out setRate, null);
}
```

## 火控与弹药的职责

`VanillaFireControlApi.TryGetTdc` 和 `TryGetFireControlBoxes` 获取艇上可选的原版组件。艇型选择复用原版 TDC 或提供自己的数字火控子系统。火控演算、鱼雷参数、制导行为和弹药定义由对应内容包拥有。

`TorpedoTubeApi.GetTorpedoTubes` 提供原版管组的组件引用。`TryGetTubeState` 返回当前弹药、原版管状态、装填与注水状态。`GetCompatibleStoredAmmo` 从所属管组的原版储位枚举兼容物品。弹药包可按原版 `StoredTorpedo.TypeName` 注册 `RegisterAmmoCompatibility`，在原版槽位规则上附加限制。原版储位检查、自动装填和 `IsAmmoCompatible` 共用这项限制。自动装填选择第一根有兼容库存的可用发射管，并保留原版弹药优先级。规则回调只用于判断，可在选弹时多次调用。释放注册后恢复原版规则。

`RequestNativeLoad(tube, ammo, actor, warm = false)` 校验管状态、原版储位和预约，再把选中的物品和目标管提交给原版搬运及装填动作。`actor` 传 `null` 时由全艇队列调度。可用原版动作进度和 `StationApi.TryCancelQueuedNativeAction` 跟踪或取消已入队的请求。`TryRequestNativeLaunch(depth, speed, salvoSpread)` 接受火控包已准备好的游戏参数，并对原版已标记且注水完成的管提交原版发射请求。散布角以度为单位，随本次请求传入原版齐射流程。游戏界面发起的原版请求使用管组当时的散布设置。
